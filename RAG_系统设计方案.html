1系统概述与设计目标

本系统是一个面向企业内部的检索增强生成（RAG）个人知识问答平台，将企业文档、个人笔记、技术资料等非结构化数据转化为可问答的知识库，通过大语言模型生成精准、可溯源的回答。

核心设计目标

  • 精准性：回答基于检索到的真实文档片段，减少幻觉，每条回答附引用来源
  • 多格式：支持 PDF、Word、Excel、PPT、Markdown、HTML、图片等主流格式
  • 高性能：查询 P99 延迟 < 3s，支持百万级文档Chunk的向量检索
  • 私有化：全栈开源方案，支持完全离线部署，数据不出域
  • 可扩展：微服务架构，各组件独立扩缩容，支持水平扩展
  • 易用性：提供对话式 Web UI，支持多轮对话、追问、引用查看

4文档处理层设计

4.1 智能分块策略 (Chunking)

分块是 RAG 系统最关键的环节之一，直接影响检索质量和生成效果。

策略方法适用场景推荐
固定长度分块按 Token 数切分，带重叠窗口快速原型、均匀文本初始方案
语义分块按句子/段落语义边界切分大多数文档推荐
标题层级分块按 Markdown/Word 标题树切分技术文档、报告推荐
表格分块整表保留或按行切分Excel、财务报表按需
递归分块先大块再切小块，保留层级长文档、复杂结构进阶

推荐分块参数

  • Chunk Size：512-1024 tokens（中文约 350-700 字）
  • Overlap：chunk_size 的 10-15%，保证上下文连续性
  • 最小 Chunk：不低于 100 tokens，避免碎片化
  • 层级关系：记录 parent_chunk_id，支持父子检索

4.2 向量化 (Embedding)

  • 模型选择：BGE-M3（1024维，支持中英多语言，开源可私有化）
  • 批量推理：使用 GPU 批量编码，单批 64-128 条
  • 增量更新：文档修改后只重新编码变化的 chunk
  • 多向量索引：同时生成 dense + sparse 向量，支持混合检索

4.3 元数据提取

每个 Chunk 关联以下元数据，用于检索过滤和结果展示：

  • 文档级：doc_id、文件名、格式、来源、上传时间、作者
  • Chunk 级：chunk_id、page_num、section_title、char_offset
  • 业务级：知识分类标签、权限组、有效期
注意：文档清洗阶段必须去除页眉页脚、水印、重复空行等噪声内容，否则会严重干扰检索质量。建议增加内容质量评分，低质量 Chunk 不入库。

6检索层设计

检索层是 RAG 系统的核心竞争力，直接决定了回答质量。本系统采用多路召回 + 混合检索 + 重排序的三阶段检索架构。

6.1 查询理解与改写

  • Query Expansion：使用 LLM 扩展同义词和相关词
  • HyDE (Hypothetical Document Embedding)：先让 LLM 生成假设性回答，用回答的向量去检索
  • Multi-Query：将一个查询改写为多个子查询，分别检索后合并
  • 意图识别：判断查询类型（定义/对比/列表/推理），调整检索策略

6.2 混合检索 (Hybrid Search)

检索方式原理优势权重
稠密向量检索语义相似度 (Cosine)理解语义、抗拼写错误0.6
稀疏检索 (BM25)关键词匹配 + TF-IDF精确匹配专有名词0.3
元数据过滤属性精确匹配缩小范围、权限控制过滤
 
# 混合检索伪代码
def hybrid_search(query: str, top_k: int = 50):
    # 1. 向量检索
    query_embedding = bge_m3.encode(query)
    vec_results = milvus.search(
        collection="knowledge_chunks",
        data=[query_embedding],
        limit=top_k * 2,
        filter=f"category == '{category}'"  # 元数据过滤
    )

    # 2. BM25 检索
    bm25_results = elasticsearch.search(
        index="knowledge_chunks",
        body={"query": {"match": {"content": query}}},
        size=top_k * 2
    )

    # 3. 融合排序 (RRF - Reciprocal Rank Fusion)
    fused = rrf_merge(vec_results, bm25_results, k=60)

    # 4. 重排序
    reranked = bge_reranker.rerank(
        query=query,
        documents=[r.content for r in fused[:top_k]],
        top_n=10
    )
    return reranked

6.3 重排序 (Reranking)

  • 模型：BGE-reranker-v2-m3（Cross-Encoder 架构，多语言）
  • 输入：Query + 每个候选 Chunk 的 Pair
  • 输出：相关性分数（0-1），按分数降序排列
  • 数量控制：对 Top-50 候选重排，取 Top-5~10 进入生成
  • 性能：GPU 推理，50 条 < 200ms
为什么需要重排序？向量检索速度快但精度有限，BM25 精确但缺乏语义理解。Reranker 作为 Cross-Encoder，将 Query 和 Document 联合编码，精度远高于双塔模型，但计算量大，因此只对少量候选重排。

7生成层设计

7.1 Prompt 工程

SYSTEM_PROMPT = """你是一个企业知识问答助手。请根据以下检索到的知识片段回答用户问题。

规则：
1. 只基于提供的知识片段回答，不要编造信息
2. 如果知识片段中没有相关内容，明确告知"未找到相关信息"
3. 回答末尾标注引用来源，格式：[来源: 文件名, 第X页]
4. 回答简洁准确，避免冗余

知识片段：
{context}

用户问题：{question}
"""

7.2 上下文组装策略

  • Token 预算：上下文总 Token 数控制在 LLM 上下文窗口的 60% 以内
  • 排序优先：Reranker 分数最高的 Chunk 排在最前面（Lost in the Middle 问题）
  • 去重：相似度 > 0.9 的 Chunk 只保留一个
  • 补充上下文：通过 parent_chunk_id 拉取父级 Chunk 补充上下文
  • 对话历史：最近 3-5 轮对话作为上下文

7.3 引用溯源

每个回答附带引用信息，用户可点击查看原文出处：

  • 回答中每个关键观点标注 [1] [2] 等引用编号
  • 引用列表展示：文件名、页码、Chunk 原文摘要
  • 支持点击跳转到原文档对应位置

7.4 LLM 推理优化

  • 推理引擎：vLLM（PagedAttention，高吞吐）
  • 量化：INT8/INT4 量化，降低显存占用
  • 流式输出：SSE 流式返回，用户首字延迟 < 1s
  • 并发控制：请求队列 + 限流，避免 OOM

13安全与合规

13.1 数据安全

  • 传输加密：全站 HTTPS (TLS 1.3)，内部服务间 mTLS
  • 存储加密：MinIO 服务端加密 (SSE-S3/KMS)
  • 敏感数据脱敏：文档入库前可选 PII 脱敏
  • 审计日志：记录所有文档操作和查询行为

13.2 访问控制

  • 认证：JWT + 可选 OAuth2/SSO 集成
  • 授权：RBAC 角色模型 + 文档级 ACL
  • API 限流：令牌桶限流，按用户/IP 双维度
  • 防注入：输入校验 + Prompt 注入防护

13.3 合规要点

  • 全栈开源组件，无数据外发风险
  • LLM 私有化部署，对话数据不出域
  • 支持数据导出和完全删除（GDPR 兼容）
  • 日志脱敏，不记录用户查询原文（可选）
